## 二、切换时的摩擦清单（他们实际抱怨什么）

1. **上下文断损**：换 agent ≈ fresh start + 重新解释项目——mida-context 的开场白就是这句话（「Switch AI coding agents without starting over」）；Omnara 线「local and remote dev feel more disconnected」是同一摩擦的另一面
2. **会话散落、格式互不相通**：每家自有存储与格式，无法互看互搜——我们的核心场景（1008 轮已实机验证接管/寄存/接力）
3. **coping 全靠手搓**：AGENTS.md / CLAUDE.md 当共享修正清单（「把你自己都要重复说的话写进去」）；slack/tmux/tailscale 自制远程；编排工具各管一家
4. **管理成本**：agent 跑偏要盯要救；crystal/vibe-kanban 的 issue 区大量「会话起不来/权限切换丢/提交信息乱」类运维痛点

## 三、竞争动态（本轮新增名字）

| 项目 | 量级 | 定位 | 与我们的关系 |
|------|------|------|--------------|
| **mida-context**（damli40） | 1★ 新品 | **user-owned/加密 context layer**；hooks 自动存 handoff（objective / progress / decisions / **rejected approaches** / next step），限额切换场景 | **概念最同构**：字段与六段卡几乎一一对应、同样打「user-owned 本地信任」。量极小、刚起步——观察名单置顶 |
| Omnara（YC S25） | 147 分发布 | harness-agnostic **远程管理**（手机 App/沙箱/preview URL/订阅制） | 不冲突：它做「随时随地管理」，不做跨家语义接管；隐私质疑集中（chats 存第三方 DB）——反衬我们本地总线的信任位 |
| crystal / vibe-kanban / orchestrator | 26/13/9 条 issue 活跃 | 多会话并行编排（worktree/看板） | 编排是「同时开多个」，我们是「跨家接力」——相邻不重叠 |

> 生态总评：**coping 工具带**（远程管理类）已经红海；**跨家语义接管 + 本地信任**位仍是空档，且本轮拿到两枚独立验证（cc-sessions #43 用户逐字请求 + mida-context 独立构建）。

## 四、对 0.2.x 的产品含义

**已覆盖 ✓（本轮被二次验证，不改）**：
- 跨家接管/寄存/接力闭环（mida-context 独立验证同一需求）
- 本地文件总线的隐私信任位（HN 线「chats 不去第三方」诉求天然满足——面板回环、零外联）
- rejected approaches 写进警告段（写卡纪律 7/8 条，与 mida 字段设计同构）

**新候选（低成本，0.2.x 观察项）**：
1. **限额切换引导（文案级）**：/handoff 的寄存确认文案可补一句「目标 harness 装有本插件即可 /inbox 取件接力」——让限额切换者知道接力和他有关
2. **移动消费面（文档级）**：HANDOFF_HOME 指同步盘后，手机文件查看器即可读卡——README 一句话宣称「手机看卡/手机上开 agent 取件」，不做 App
3. **mida-context 盯梢**：与 harness-remote 同级观察对象；若它把「context layer」做成通用协议，就是正面对撞信号

**明确不追**：远程管理/沙箱/移动 App 赛道（Omnara/Happy/VibeTunnel/openchamber 红海，且偏离只读接管定位）；harness-agnostic 远程执行（同前）；A2A 实时会话（git-conversation 类玩法，与异步接力定位不同）。
