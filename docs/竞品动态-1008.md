## 生态位重估：什么仍是独占的

浏览器层（列表/搜索/预览）已被 agent-sessions 893★ 定价为**必备品**——我们这轮把面板第五区补上属于「追平预期」，不是创新。逐项核对本轮全部样本后，以下四点**仍然只有我们有**：

1. **harness 内嵌**：全部 9 个样本都是独立 app/CLI/桌面端，无一以插件形态长在宿主里（DSH 设置卡 + slash 纪律 + 取件在会话内发生）。
2. **开放文件总线协议（handoff:1）**：harness-remote 的 bounded context + lineage 在语义上最接近，但 lineage 记在它自家控制面、第三方工具读不到；我们的六段卡 + YAML frontmatter + `~/.handoff`（可指同步盘）是任何工具可实现的版本化开放协议，消费即弃语义独此一家。
3. **证据账本四态**：9 个样本无一做「逐陈述 HISTORY_REPORTED/CURRENT_OBSERVED/MISMATCH/UNAVAILABLE」审计语义；harness-remote 的 "checks already run" 只是内容类型清单。
4. **安全闸族**：密钥闸/空壳卡闸/读侧尺寸闸/连接级回环闸——全样本空白（它们读自家盘不设防可以理解，交接面产品不设防是真空）。

另注意：**写别家会话存储**（harness-remote continuation、cc-sessions 转换、casr、memex transfer）与**我们只读+蒸馏**是两条路线的根本分歧——前者体验原生但有保真风险（casr #10 案底），后者永远有效但依赖模型蒸馏质量（跟着模型能力升级）。

## 对我们的三个动作建议

1. **README「竞品与差异化」小节补本轮名单**：10-03 只补了转换器路线的对比；harness-remote（bounded context vs 协议卡、闭面 lineage vs 开放总线）与 agent-sessions（只读浏览 vs 浏览+接管）值得各给一句，中英同步。
2. **盯 harness-remote 的 continuation 上下文格式**：若它日后把该格式独立成开放规范，就是与我们正面对撞的信号——我们的应对是把 `handoff: 1` 的「第三方可采用」叙事做实（README 占位声明 + issue 登记采用列表，10-03 动作 #1 的延续）。
3. **memex transfer / mcp-agent-mail 是两个「相邻方向」素材**：transfer 验证了「跨家搬运有真实需求但难做无损」；mcp-agent-mail 验证了「agent 间协调」需求。可在需求调研文档里各记一笔，暂不动代码。

## 上游原生功能风险

- 本轮顺带核实：各家 resume 仍是自家 `--resume`；agent-sessions 5.5.3 对 DeepSeek Harness 仅只读（无续跑——与 1003 记录一致，上游无原生导出）。
- 最大风险项不变：任一头部 harness 原生支持「会话导出/跨工具续跑」。harness-remote 的增长速度（403★ + 多端产品化）意味着「第三方把这件事做好」的窗口比「上游自己做」更先关闭。
